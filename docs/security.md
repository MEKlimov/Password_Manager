# Архитектура безопасности "Умного менеджера паролей"

[cite_start]Данный документ описывает архитектуру безопасности, схемы шифрования и хранения данных, а также содержит отчет о тестировании безопасности приложения [cite: 114-116, 118].

## 1. Описание архитектуры безопасности
Приложение спроектировано по принципу "нулевого доверия" к локальному хранилищу. Основной стек безопасности построен на базе криптографического провайдера **Bouncy Castle**. 
[cite_start]Ни один пользовательский пароль не сохраняется в базе данных в открытом виде (plain text)[cite: 108]. Расшифровка происходит исключительно в оперативной памяти в момент запроса пользователя (например, при редактировании или копировании в буфер обмена).

Дополнительные меры защиты (Группа А):
* [cite_start]**Аудит безопасности:** Все попытки входа (успешные и неуспешные) логируются в БД с фиксацией локального времени[cite: 22].
* [cite_start]**Защита буфера обмена:** Скопированные пароли автоматически удаляются из системного буфера обмена через 30 секунд после копирования[cite: 23].

## 2. Схемы шифрования
[cite_start]В приложении используется современная гибридная криптография[cite: 24, 46, 109].

### 2.1 Шифрование Мастер-пароля (PBKDF2)
Мастер-пароль не хранится нигде. При первом запуске:
1. Генерируется криптографически стойкая случайная "соль" (16 байт) через `SecureRandom`.
2. [cite_start]Пароль пропускается через алгоритм **PBKDF2WithHmacSHA256** (100 000 итераций)[cite: 24].
3. Полученный 256-битный хэш и соль кодируются в Base64 и сохраняются в БД.
[cite_start]*Защита от Timing Attacks:* Сравнение хэшей при входе делегировано встроенным механизмам провайдера Bouncy Castle[cite: 110].

### 2.2 Шифрование данных (AES-256-GCM)
[cite_start]Пользовательские пароли от сервисов шифруются симметричным алгоритмом **AES-256 в режиме GCM** (Galois/Counter Mode), который обеспечивает не только конфиденциальность, но и аутентификацию данных[cite: 46, 109].
1. Ключ шифрования (`SecretKey`) динамически генерируется в памяти из введенного Мастер-пароля.
2. Для каждой записи создается уникальный вектор инициализации (IV) длиной 12 байт.
3. Длина тега аутентификации (MAC) составляет 128 бит.
4. В БД сохраняется конкатенированная строка `[IV + CipherText]` в формате Base64.

## 3. Схема хранения данных
[cite_start]В качестве хранилища используется локальная реляционная база данных **SQLite** (`passwords.db`)[cite: 44]. [cite_start]Для защиты от SQL-инъекций все без исключения запросы реализованы через параметризованные `PreparedStatement`[cite: 111].

Структура БД состоит из трех таблиц:
1. `settings` (key TEXT, value TEXT) — хранит `salt` и `hash` мастер-пароля.
2. [cite_start]`records` (id INTEGER, category TEXT, title TEXT, username TEXT, encrypted_password TEXT) — хранит зашифрованные записи[cite: 54, 55].
3. `audit_log` (id INTEGER, timestamp DATETIME, status TEXT) — журнал попыток доступа.

## 4. Отчет о тестировании безопасности
**Статический анализ кода:**
* Прямое использование строк конкатенации в SQL-запросах не выявлено. [cite_start]Везде применяется `PreparedStatement`[cite: 111].
* Пароли из UI (JavaFX `PasswordField`) не кэшируются в явном виде.

**Ручное тестирование (Penetration Test):**
1. *Анализ файла БД:* Открытие файла `passwords.db` через сторонний клиент SQLite (DBeaver) показало, что столбец `encrypted_password` содержит нечитаемый Base64-код. [cite_start]Исходные пароли скомпрометировать невозможно без знания Мастер-пароля[cite: 72, 81].
2. [cite_start]*Попытка подбора (Bruteforce):* Неверный ввод пароля корректно отторгается системой, а в таблицу `audit_log` вносится запись об "ОШИБКЕ ДОСТУПА"[cite: 22].
3. [cite_start]*Утечка через буфер обмена:* Ожидание 30 секунд после копирования пароля из программы подтвердило его автоматическое стирание из буфера macOS[cite: 23].
